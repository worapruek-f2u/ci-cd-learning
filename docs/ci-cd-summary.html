CI/CD กับ GitHub — สรุปสิ่งที่ทำมา

โปรเจกต์ NestJS → GitHub Actions → GHCR → Render · repo: worapruek-f2u/ci-cd-learning · เว็บ: ci-cd-learning-0wkh.onrender.com/hc

branch + commit→ เปิด PR→ CI: lint · test · build→ merge เข้า main→ CD: build image → GHCR→ Render deploy
จำเป็น ขาดไม่ได้ ไม่มีแล้ว pipeline ไม่ทำงาน ควรทำ ข้ามได้ แต่งานจริงเกือบทุกทีมทำ ข้ามได้ ของเสริม ทำตอนพร้อม

1. ขั้นตอนทั้งหมด ทีละบท

บททำอะไรระดับหมายเหตุ
0สร้างโปรเจกต์ + .gitignoreจำเป็นไม่มี .gitignore = node_modules หลุดขึ้น git
0.gitattributes (บังคับ LF)ควรทำกันปัญหา Windows (CRLF) กับ Linux runner (LF) ต่างกัน
1สร้าง repo เปล่าบน GitHub + git push -u origin mainจำเป็นอย่าติ๊ก README ตอนสร้าง ถ้าในเครื่องมีโค้ดอยู่แล้ว
2.github/workflows/ci.ymlจำเป็นโฟลเดอร์ตายตัว ชื่อไฟล์ตั้งอะไรก็ได้ (.yml/.yaml)
2script lint:check (ไม่มี --fix)ควรทำCI ต้อง “ฟ้อง” ไม่ใช่แก้ให้เงียบ ๆ
2step E2E testข้ามได้มีแล้วดี แต่ถ้า e2e ช้า/ต้องใช้ DB อาจแยกไปรันทีหลัง
3Ruleset: Require pull requestควรทำทำงานคนเดียวข้ามได้ แต่ทีมควรมีเสมอ
3Ruleset: Require status check build-and-testควรทำตัวนี้แหละที่ทำให้โค้ดพังเข้า main ไม่ได้จริง
3Squash merge · Auto-merge · Auto-delete branchข้ามได้ความสะดวก/ความสะอาดของ history
4Dockerfile + .dockerignoreจำเป็นจำเป็นเมื่อ deploy แบบ image (Render, Cloud Run, k8s)
4Multi-stage build · USER nodeควรทำimage เล็กลง ปลอดภัยขึ้น
4cd.yml job docker → push GHCRจำเป็นต้องมี permissions: packages: write
4tag image ด้วย ${{ github.sha }}ควรทำรู้ว่ารันโค้ด commit ไหน + rollback ได้
5GHCR package เป็น Publicจำเป็น**ถ้า private ต้องใส่ credential ใน Render แทน
5Render Web Service จาก Existing Imageจำเป็นแอปต้องฟัง process.env.PORT
5Secret RENDER_DEPLOY_HOOK_URLจำเป็นห้ามใส่ใน code เด็ดขาด
5job deploy (needs: docker)จำเป็นไม่มี needs = deploy ก่อน image เสร็จ
5environment: productionข้ามได้ได้หน้า Deployments + ตั้งให้ต้อง approve ก่อน deploy ได้
5ส่ง imgURL=<sha> ไป Renderข้ามได้ไม่ส่ง = Render ดึง :latest แทน
—Endpoint /hc (health check)ควรทำตั้งเป็น Health Check Path ใน Render ได้ → deploy พังจะไม่สลับไปใช้ตัวใหม่

2. ไฟล์สำคัญในโปรเจกต์

.github/workflows/ci.yml — ตรวจโค้ด

on:
  push:         { branches: [main] }   # ตรวจ main หลัง merge
  pull_request: { branches: [main] }   # ตรวจทุก PR
jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 24, cache: npm }
      - run: npm ci
      - run: npm run lint:check
      - run: npm test
      - run: npm run test:e2e
      - run: npm run build

.github/workflows/cd.yml — ส่งของขึ้น server

on:
  push: { branches: [main] }           # เฉพาะเมื่อเข้า main
jobs:
  docker:
    permissions: { contents: read, packages: write }
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3       # login ghcr.io ด้วย GITHUB_TOKEN
      - uses: docker/build-push-action@v6  # tag :latest + :<sha>
  deploy:
    needs: docker                          # รอ docker เสร็จก่อน
    environment: production
    steps:
      - run: curl -fsS -X POST "$DEPLOY_HOOK&imgURL=..."

3. Cheat sheet

YAML ของ GitHub Actions

on:เมื่อไหร่จะรัน (push, pull_request, schedule, workflow_dispatch = กดเอง)
jobs:งานแต่ละชุด — รันพร้อมกัน ถ้าไม่ใส่ needs
runs-on:เครื่องที่ใช้ (ubuntu-latest ถูก/เร็วสุด)
steps:ทำทีละขั้นบนลงล่าง ขั้นไหนพัง ที่เหลือ skipped
uses:เรียก action สำเร็จรูป owner/repo@version (หาจาก Marketplace)
run:รันคำสั่ง shell (bash บน ubuntu)
${{ }}ดึงค่า: github.sha, github.repository, secrets.X
needs:ให้ job นี้รอ job อื่น
permissions:สิทธิ์ของ GITHUB_TOKEN (ขอเท่าที่ใช้)

Flow ประจำวัน

git switch main && git pull           # 1. เริ่มจาก main ล่าสุดเสมอ
git switch -c feat/my-thing           # 2. แตก branch
# ... เขียนโค้ด ...
npm run lint:check && npm test        # 3. ตรวจในเครื่องก่อน push (ประหยัดรอบ CI)
git commit -am "feat: my thing"
git push -u origin feat/my-thing      # 4. push branch
# 5. เปิด PR → (Enable auto-merge) → CI ✅ → Squash and merge
git switch main && git pull           # 6. ดึงผล merge กลับมา

Conflict

git fetch origin
git merge origin/main        # แก้ไฟล์ที่มี <<<<<<< ======= >>>>>>>
npm test
git add . && git commit && git push   # CI รันใหม่อัตโนมัติ

4. ต้องรู้ shell แค่ไหน?

ไม่ต้องเก่ง แต่ต้องอ่านออก — ส่วนใหญ่ของ workflow คือ uses: (ไม่ต้องเขียน shell เลย) ส่วน run: มักเป็นคำสั่งที่คุณพิมพ์ใน terminal ทุกวันอยู่แล้ว เช่น npm ci, npm test

shell (bash) ที่เจอบ่อยใน CI/CD มีแค่นี้:

  • curl -X POST "$URL" — ยิง HTTP (deploy hook, แจ้งเตือน Slack)
  • $VAR / env: — ใช้ตัวแปร (ส่ง secret ผ่าน env: ปลอดภัยกว่าใส่ ${{ }} ตรง ๆ ใน run:)
  • if [ -z "$VAR" ]; then ... fi — เช็กว่าตัวแปรว่างไหม
  • exit 1 — สั่งให้ step พัง (CI แดง)
  • echo "::error::ข้อความ" — ขึ้นข้อความ error สีแดงใน Annotations
  • ssh user@host "docker pull ... && docker run ..." — ถ้าวันหนึ่ง deploy ลง VPS เอง

ข้อสังเกต: runner เป็น Linux (bash) ไม่ใช่ PowerShell — คำสั่งบางตัวในเครื่อง Windows จึงใช้ใน workflow ไม่ได้ ถ้าไม่แน่ใจ ให้หา action สำเร็จรูปก่อน แทบทุกเรื่องมีคนทำไว้แล้ว

5. ข้อผิดพลาดที่เจอระหว่างเรียน

  • ลืม .gitignore — git พยายาม add node_modules ทั้งก้อน
  • กด Merge แต่ไม่กด Confirm merge — PR ยังเปิดอยู่ main ไม่เปลี่ยน
  • ลืม git pull หลัง merge — merge เกิดบน GitHub ไม่ใช่ในเครื่อง
  • push ทั้งที่ lint ไม่ผ่าน (2 รอบ) — รัน npm run lint:check ก่อน push ทุกครั้ง หรือทำ pre-commit hook (ดูข้อ 6)
  • ตั้ง approvals = 1 ตอนทำคนเดียว — merge ไม่ได้ตลอดกาล เพราะ approve PR ตัวเองไม่ได้
  • GHCR package เป็น private — Render / docker pull ขึ้น unauthorized
