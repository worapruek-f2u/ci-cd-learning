Workflow ทำงานพร้อมกันไหม & ให้ CD รอ CI

อ่านคู่กับ ci-cd-summary.html · โปรเจกต์ ci-cd-learning

1. ลำดับการทำงาน 3 ระดับ

Workflow (ไฟล์) แต่ละไฟล์ใน .github/workflows/ อิสระต่อกัน รันเมื่อ event ตรงกับ on: ของตัวเอง — ถ้าหลายไฟล์ตรงกัน รันพร้อมกัน
Job หลาย job ในไฟล์เดียว รันพร้อมกัน แต่ละ job ได้เครื่องใหม่ — ใส่ needs: เพื่อให้รอกัน (ใช้ได้เฉพาะในไฟล์เดียวกัน)
Step ใน job เดียว รันทีละขั้น บนลงล่างเสมอ ขั้นไหนพัง ขั้นที่เหลือ skipped

ตอนนี้ของเราเป็นแบบนี้

event                      ci.yml        cd.yml
เปิด PR / push เข้า PR      ✅ รัน         ❌ ไม่รัน
merge เข้า main            ✅ รัน         ✅ รัน   ← พร้อมกัน!

merge → CI (lint/test/build)   ── ถ้าแดง ❌ ...
      → CD (docker → deploy)   ── ... CD deploy ไปแล้ว 😬

ruleset บังคับ CI ผ่านที่ PR ก่อนอยู่แล้ว จึงปลอดภัยพอสมควร แต่ยังมีช่องโหว่กรณี PR A ผ่าน + PR B ผ่าน แต่รวมกันแล้วพัง — แก้ได้ 2 แบบด้านล่าง

แบบ Aworkflow_run — “ทำต่อเมื่อ CI จบ”

แก้แค่ cd.yml — ci.yml ไม่ต้องแตะ

name: CD

on:
  workflow_run:
    workflows: [CI]          # ชื่อตรงกับ "name: CI" (ไม่ใช่ชื่อไฟล์)
    types: [completed]       # trigger เมื่อ CI จบ — ทั้งผ่านและพัง
    branches: [main]

jobs:
  docker:
    if: >
      github.event.workflow_run.conclusion == 'success' &&
      github.event.workflow_run.event == 'push'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.workflow_run.head_sha }}   # commit เดียวกับที่ CI ทดสอบ

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: |
            ghcr.io/${{ github.repository }}:latest
            ghcr.io/${{ github.repository }}:${{ github.event.workflow_run.head_sha }}

  deploy:
    needs: docker
    # ... เหมือนเดิม แต่เปลี่ยน github.sha → github.event.workflow_run.head_sha

หน้า Actions

CI  ✅  (lint/test/build)
  └─► CD ✅  (docker → deploy)     ← 2 run แยกกัน
⚠️ ต้องระวัง
  • ห้ามใช้ github.sha — ใน workflow_run มันคือ commit ล่าสุดของ main ตอน CD เริ่ม อาจไม่ใช่ commit ที่ CI ทดสอบ → ใช้ workflow_run.head_sha
  • workflow_run อ่านไฟล์จาก main เท่านั้น → ทดสอบบน PR ไม่ได้ ต้อง merge ก่อนถึงเห็นผล
  • ถ้ามีคนเปลี่ยน name: CI → CD เงียบหายไปเลย ไม่มี error

แบบ CReusable workflow — “CD เรียกใช้ CI” แนะนำ

ขั้นที่ 1 · ci.yml — เปิดให้ถูกเรียกได้

name: CI

on:
  pull_request:
    branches: [main]
  workflow_call:             # อนุญาตให้ workflow อื่นเรียกไฟล์นี้
  # push: main  ← ลบออก เพราะ CD เรียกให้แทน (ไม่ลบ = CI รัน 2 รอบ)

jobs:
  build-and-test:
    # ... steps เหมือนเดิมทุกอย่าง

ขั้นที่ 2 · cd.yml — เรียก CI เป็น job แรก

name: CD

on:
  push:
    branches: [main]

jobs:
  ci:
    uses: ./.github/workflows/ci.yml     # เรียกทั้งไฟล์ ci.yml เป็น job หนึ่ง

  docker:
    needs: ci                            # needs ข้ามไฟล์ได้แล้ว เพราะอยู่ run เดียวกัน
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      # ... เหมือนเดิม (ใช้ github.sha ได้ปกติ)

  deploy:
    needs: docker
    # ... เหมือนเดิม

หน้า Actions

CD:  ci / build-and-test ✅ ──► docker ✅ ──► deploy ✅     ← run เดียว เห็นทั้ง pipeline
⚠️ ต้องระวัง
  • ถ้า ci.yml ต้องใช้ secret → ส่งให้ด้วย secrets: inherit ใต้ uses:
  • ตอนเปิด PR ยังรัน CI แบบเดิม check ชื่อ build-and-test ไม่เปลี่ยน → ruleset ไม่ต้องแก้

2. เปรียบเทียบ

A workflow_runC Reusable
ไฟล์ที่แก้cd.yml อย่างเดียวci.yml + cd.yml
หน้า Actions2 run แยกกัน1 run เห็นทั้ง pipeline
commit ตรงกันแน่นอนต้องระวัง head_sha เอง✅ github.sha ปกติ
ทดสอบบน PR ได้❌ ต้อง merge ก่อน✅ ได้
เหมาะกับCI / CD คนละทีมดูแล, CD ต้องรอหลาย workflowโปรเจกต์ทั่วไป, ใช้ CI ซ้ำหลายที่

สรุป: โปรเจกต์นี้ใช้ C ดีกว่า — ไม่ต้องระวังเรื่อง sha, เห็น pipeline ในหน้าเดียว, ทดสอบบน PR ได้
